# Foto — скриншотер веб-страниц

Веб-приложение с тремя режимами:
1. **Скриншот** — делает снимок любой страницы по URL и сохраняет фото на
   устройство пользователя.
2. **HTML элемента** — извлекает полный HTML (`outerHTML`) конкретного
   элемента страницы по CSS-селектору, даже если он визуально скрыт
   (например, служебная разметка для SEO/скринридеров).
3. **Список рейсов** — находит ВСЕ повторяющиеся блоки по CSS-селектору
   (например, все карточки авиарейсов на странице поиска), разбирает из
   каждого авиакомпанию/номер рейса/вылет/прилёт/длительность/цену и
   собирает единый текстовый файл в развёрнутом или коротком формате.

## Как это работает

- Backend на Node.js/Express запускает headless Chromium (Playwright),
  открывает указанный адрес и либо делает снимок страницы, либо находит
  элемент(ы) по CSS-селектору и возвращает их разметку/разобранные данные.
- Frontend — простая HTML-страница с тремя вкладками: вводите URL (и,
  где нужно, селектор), настраиваете параметры и получаете результат —
  картинку, блок с HTML или текстовый файл — который можно сохранить.

## Установка и запуск

```bash
npm install
npm start
```

При первой установке Playwright скачает браузер Chromium (шаг
`postinstall`). Если он не запустился автоматически, выполните:

```bash
npx playwright install chromium
```

Приложение будет доступно на `http://localhost:3000`.

> ⚠️ **Важно:** это не статичная HTML-страница — снимки делает Node.js/
> Playwright-сервер (браузер сам по себе не может сфотографировать
> произвольный внешний сайт). Открывать `public/index.html` двойным
> кликом (`file://…`) нельзя — запросы к API будут падать с ошибкой
> `Failed to fetch`. Всегда заходите через адрес, который выводит
> `npm start` (`http://localhost:3000`).

## Параметры снимка

- **Вся страница целиком** — снимать всю высоту страницы или только
  видимую область (viewport).
- **Формат** — PNG или JPEG.
- **Ширина/высота** — размер окна браузера при загрузке страницы.
- **Когда считать страницу загруженной** — стратегия ожидания:
  - `load` (по умолчанию) — дождаться события загрузки страницы; подходит
    для большинства сайтов и реже всего даёт тайм-аут;
  - `networkidle` — дождаться полной тишины в сети (нет запросов ≥500мс);
    надёжнее для сайтов с "доездающим" контентом, но многие сайты (с
    рекламой/аналитикой/вебсокетами) никогда её не достигают и снимок
    упадёт по тайм-ауту;
  - `domcontentloaded` — только распарсенный HTML, самый быстрый вариант,
    но картинки/скрипты могут не успеть отрисоваться.
- **Макс. время ожидания загрузки** — сколько секунд ждать выполнения
  выбранного условия выше, прежде чем считать это тайм-аутом (5–120 сек,
  по умолчанию 45).
- **Доп. задержка перед снимком** — фиксированная пауза после загрузки
  (полезно для анимаций/ленивой подгрузки контента), до 30000 мс.
- **Прокрутить вниз перед снимком** — сколько пикселей проскроллить страницу
  вниз перед тем, как делать снимок (0–20000 px). Полезно для двух вещей:
  для обычного снимка (без «Вся страница целиком») сдвигает область
  захвата — например, чтобы убрать из кадра «прилипшую» шапку или баннер;
  а для снимка всей страницы помогает подгрузить контент, который
  появляется только при прокрутке (ленивая загрузка изображений/карточек,
  подгружаемых постранично через API). Прокрутка идёт небольшими шагами
  (не одним прыжком), с паузой после каждого — так у сайта есть время
  реально подгрузить и отрисовать очередную порцию контента, а не остаться
  "заглушками"-плейсхолдерами в кадре.
- **Клик перед снимком (X, Y)** — необязательные координаты в пикселях от
  левого верхнего угла окна браузера (то же самое, что левый верхний угол
  итогового снимка — либо текущей прокрученной области, если задан ещё и
  `scrollY`). Клик выполняется после прокрутки, прямо перед снимком —
  полезно, чтобы закрыть баннер cookies, открыть меню/подсказку или нажать
  кнопку вроде «Показать ещё». **Указывать координаты мышкой:** сделайте
  обычный снимок, затем кликните прямо по превью на странице — координаты
  клика (с пересчётом под реальный размер снимка, даже если картинка
  уменьшена под ширину экрана) сами подставятся в поля X/Y и точка
  отметится на превью красной точкой; останется нажать «Сделать
  скриншот» ещё раз, чтобы применить клик. Если включена «Вся страница
  целиком», превью может быть выше окна браузера — Y автоматически
  ограничивается высотой поля «Высота, px», поскольку сам клик на сервере
  выполняется по видимой области окна, а не по всей длинной странице.

## API

`POST /api/screenshot`

```json
{
  "url": "example.com",
  "fullPage": true,
  "format": "png",
  "width": 1280,
  "height": 800,
  "waitUntil": "load",
  "timeout": 45,
  "delay": 0,
  "scrollY": 0,
  "clickX": null,
  "clickY": null
}
```

- `waitUntil` — `load` | `networkidle` | `domcontentloaded` (по умолчанию `load`)
- `timeout` — секунды, 5–120 (по умолчанию 45)
- `delay` — миллисекунды, 0–30000 (по умолчанию 0)
- `scrollY` — пиксели прокрутки вниз перед снимком, 0–20000 (по умолчанию 0).
  Выполняется после ожидания загрузки и `delay`, шагами по ~700px с паузой
  и попыткой дождаться "тишины в сети" после каждого шага (плюс финальная
  пауза до 3с) — чтобы контент, подгружаемый постранично по мере
  прокрутки (типичный infinite scroll), успел реально прогрузиться, а не
  остался "заглушками"-плейсхолдерами на снимке.
- `clickX`, `clickY` — необязательные координаты клика в пикселях (0 до
  ширины/высоты окна браузера). Заданы оба — клик выполняется после
  прокрутки и короткой паузы после неё, прямо перед снимком. Клик "вслепую"
  по координатам (не по CSS-селектору) — работает независимо от того, что
  именно находится в этой точке, и не завершает запрос ошибкой, если там
  вообще ничего интерактивного нет.

Ответ — бинарные данные изображения (`image/png` или `image/jpeg`) с
заголовком `Content-Disposition: attachment`, либо JSON `{ "error": "..." }`
при ошибке.

`POST /api/extract-element`

```json
{
  "url": "example.com",
  "selector": "h1",
  "waitUntil": "load",
  "timeout": 45,
  "delay": 0
}
```

Ответ (200):

```json
{
  "url": "https://example.com/",
  "selector": "h1",
  "matchCount": 1,
  "html": "<h1>...</h1>",
  "text": "...",
  "filename": "example.com_2026-01-01T00-00-00-000Z.html"
}
```

Если селектор ничего не находит — ответ `404` с `{ "error": "..." }`.
Если селектору соответствует несколько элементов, возвращается первый
(`matchCount` показывает общее число совпадений).

`POST /api/extract-flights`

```json
{
  "url": "example.com",
  "selector": null,
  "format": "detailed",
  "waitUntil": "load",
  "timeout": 45,
  "delay": 0
}
```

- `selector` — необязательный CSS-селектор карточки рейса. Если не задан
  (или пустая строка) — карточки ищутся **автоматически** (см. ниже), без
  какого-либо ручного ввода селектора.
- `format` — `detailed` (развёрнутый) | `short` (короткий), по умолчанию `detailed`.

Ответ (200):

```json
{
  "url": "https://example.com/",
  "selector": null,
  "autoDetected": true,
  "format": "detailed",
  "matchCount": 2,
  "entries": [ { "airline": "...", "flightNumber": "...", "flightNumberIsAirlineCode": false, "departure": {...}, "arrival": {...}, "duration": "...", "price": "...", "stopsText": "...", "hasStop": false } ],
  "text": "Thai Lion Air\nFlight: SL100\n...",
  "filename": "example.com_2026-01-01T00-00-00-000Z.txt"
}
```

`text` — уже готовое содержимое файла: все найденные блоки в выбранном
формате, разделённые пустой строкой.

**Как ищутся карточки (без селектора).** Каждая карточка рейса у trip.com
целиком помечена готовым для скринридеров текстом в `aria-label` вида
`"Flight departing from X at <дата-время> ... arriving ... at
<дата-время>"`. Это гораздо надёжнее CSS-класса — не зависит от хэшей
сборки сайта. Автопоиск сканирует все элементы с `aria-label`, находит
подходящие по этому шаблону и оставляет только самые "внутренние"
совпадения (без внешних обёрток). Если на странице другая структура и
автопоиск ничего не нашёл — можно передать `selector` вручную (как раньше).

**Как устроен парсинг остальных полей.** Опирается на устойчивые
признаки — `data-testid` и `aria-label`/`role` — а не на хэшированные
CSS-классы вида `foo_8688`, которые меняются между сборками сайта:
- **Авиакомпания** — `[data-testid="flights-name"]` внутри блока (для
  кодшеринговых рейсов — уже готовая строка через запятую, например
  `"Thai Vietjet, Sun PhuQuoc Airways"`).
- **Вылет/прилёт** — контейнеры с классом, содержащим `is-departure` /
  `is-arrival`; название аэропорта — их `aria-label`, точное время —
  `data-testid="flight-time-<дата-время>"`, код аэропорта — соседний
  `span` с классом, содержащим `flight-info-stop__code`.
- **Длительность** — берётся из отдельного элемента
  `[data-testid="flightInfoDuration"]` (короткий формат вида `2h 25m`,
  одинаково надёжно и для прямых, и для стыковочных рейсов).
- **Пересадка/стыковка** — `[data-testid="stopInfoText"]`: `"Direct"` для
  прямого рейса или описание пересадки (город + длительность стыковки,
  например `"18h 40m in Phu Quoc Island"`) для рейса со стыковкой. Для
  стыковочных рейсов в файл добавляется отдельная строка `Stop: ...`
  (`hasStop: true` в ответе API), для прямых — не добавляется.
- **Цена и описательное предложение о рейсе** — разбираются из "родного"
  `aria-label` самого блока (у trip.com он уже содержит готовый текст вида
  `This is a nonstop flight with a duration of 2h 25m` / `The flight
  duration is 18 hours 40 minutes, including a layover of ...` и
  `One-way price: RUB 8,933`); в развёрнутом формате выводятся как есть,
  даже если сама формулировка на сайте не идеальна (случаются
  непереведённые плейсхолдеры вроде `${2}` — это особенность разметки
  trip.com, не ошибка парсинга).
- **Номер рейса** — на странице результатов поиска trip.com в списке
  карточек его физически нет в разметке (только название авиакомпании).
  Поэтому: сначала ищется эвристически (элементы с явным намёком в
  `data-testid`/`class` вида `flight-no`, затем по всему тексту/атрибутам
  блока по паттерну «2–3 буквы + 2–4 цифры», с отсевом валютных кодов);
  если не найдено — используется **код авиакомпании** из бокового списка
  фильтров (`[data-testid="filter_airline"]`, атрибут `data-code` + его
  `aria-label` с полным названием) как более честный запасной вариант, чем
  прочерк (`flightNumberIsAirlineCode: true` в ответе — это не настоящий
  номер рейса, а код перевозчика, для кодшеринга — несколько кодов через
  `/`). Если не найдено вообще ничего — в файле будет прочерк `—`.

⚠️ Эта логика работает надёжно только на сайтах с похожей (trip.com-style)
разметкой. На структуре другого сайта поля могут не заполниться —
`/api/extract-element` (второй режим) в этом случае подойдёт лучше, чтобы
сначала посмотреть, какой именно HTML отдаёт страница.

## Деплой на хостинг

⚠️ Это **не статичный сайт** — приложению нужен постоянно работающий
Node.js-сервер, который умеет запускать headless-браузер (Chromium).
Поэтому подойдёт хостинг с поддержкой Docker/Node-серверов, а не
статические хостинги вроде GitHub Pages/обычного Netlify.

В репозитории уже есть `Dockerfile` — образ на базе официального
`mcr.microsoft.com/playwright`, в котором Chromium и все системные
зависимости уже установлены (это решает проблему со скачиванием
браузера, которая может возникать при обычном `npm install` на
некоторых хостингах).

### Вариант 1 — Render.com (бесплатный тариф есть)

1. Зайдите на [render.com](https://render.com) и войдите через GitHub.
2. **New +** → **Web Service** → выберите репозиторий `foto`.
3. Render сам обнаружит `Dockerfile` — оставьте Environment = **Docker**.
4. Ветку укажите `claude/web-screenshot-app-pa8x3c` (или ту, куда смёржите изменения).
5. Instance Type можно оставить Free для тестов.
6. **Create Web Service** — через несколько минут получите публичный URL
   вида `https://foto-xxxx.onrender.com`.

Порт слушать не нужно настраивать отдельно — Render передаёт его через
переменную окружения `PORT`, а сервер уже её читает (`server.js`).

### Вариант 2 — Railway.app

1. [railway.app](https://railway.app) → **New Project** → **Deploy from
   GitHub repo** → выберите `foto` и нужную ветку.
2. Railway автоматически найдёт `Dockerfile` и соберёт образ.
3. После деплоя во вкладке **Settings → Networking** сгенерируйте публичный
   домен.

### На что обратить внимание

- **Память.** Chromium + Node в среднем требуют около 512 МБ–1 ГБ RAM на
  один одновременный снимок. На самых урезанных бесплатных тарифах
  возможны падения по нехватке памяти — если это произойдёт, переключитесь
  на платный план побольше.
- **"Холодный старт".** Бесплатные тарифы (например, Render Free) обычно
  "усыпляют" сервис при простое — первый запрос после паузы может занять
  10–30 секунд на "пробуждение" контейнера, это нормально.
- **Локальная сборка Docker-образа** (проверить перед деплоем):
  ```bash
  docker build -t foto .
  docker run -p 3000:3000 foto
  ```
  затем откройте `http://localhost:3000`.
